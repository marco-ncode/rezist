## [Unreleased]

### Added
- **RZ-144 — Wire ability-unlock enforcement** (`game/core/run/RunState.gd`, `game/scripts/mission/MissionController.gd`, `game/scripts/ui/Armory.gd`, `schemas/save_file.schema.json`): `RunState` gained a persisted `_ability_unlocks` table (`has_ability_unlocked()`/`unlock_ability()`, `SAVE_VERSION` bumped to 3 with a migration default of `{}` for an older save) tracking which commanders have purchased their class's ability. `MissionController._squad_ability_unlocked()` now gates ability activation on the squad being level 2+ (GDD: "L2: class specialization unlocked, ability purchasable") *and* having purchased it — wired into `_on_ability_button_pressed()`, `_on_tile_clicked()`'s ability branch (defensive re-check), and the HUD ability button's ready-state/label ("Ability (Locked)" when a selected squad hasn't unlocked it). Before this, every class's ability worked unconditionally from mission 1 regardless of level or purchase. The Armory's Abilities tab (RZ-085) is now a real purchase: spends `Economy.ability_cost()`, calls `RunState.unlock_ability()`, only offers the purchase once the squad is level 2+ and the ability actually has an `Ability` implementation (Focused Volley/Line Charge still don't, RZ-048 — shown as "not yet implemented" instead of a buyable option). **Behavior change:** the vertical slice's 3 starting commanders begin at level 1, so Breach is no longer available on mission 1 of a fresh run — reaching level 2 and buying it in the Armory is now required, matching design intent that was previously unenforced. Deliberately deferred out of RZ-085 since it touches the same ability-activation code path RZ-143 found silently broken for months; added round-trip/migration test coverage in `test_save_load_roundtrip.gd` before landing it.
- **RZ-086 — Roster/Commander screen** (`game/scenes/Roster.tscn`, `game/scripts/ui/Roster.gd`, `game/scripts/ui/MissionPrepController.gd`): new Roster screen (UX_UI.md §7), reached from a new "Roster" button on Mission Prep's bottom bar alongside Armory's (`[Back]` returns there too). Lists every alive commander (name/class/level, trait name+description or "None", relic name or "None", squad size as dots) and, below a separator, every fallen commander by name — `RunState.commanders` never removes a dead entry, only its roster metadata, so this is a genuine permanent history (GDD pillar 2). Squad size deliberately never shows a "(5/6)" fraction like the wireframe does — ADR-0005 bans a number for squad strength on every other screen, and this one isn't an exception. The wireframe's "died Mission 4 (Brute)" cause-of-death annotation is also omitted — nothing anywhere tracks which mission or enemy killed a commander; `RunState.on_commander_died()` only erases roster metadata and emits a signal. Adding that tracking is a real feature, not folded into this screen.
- **`docs/ART_BIBLE.md` §8 — Character Art Production Spec**: concrete production specs for the eventual real art pass (RZ-122) — canvas size, file format, perspective/framing derived from the actual engine rendering approach (`TECHNICAL_DESIGN_DOCUMENT.md`'s 2.5D top-down grid, not a classic isometric projection), and the full character roster (4 player classes × their levels, 8 zombie types, 4 safehouse damage states) with each one's silhouette requirement cross-referenced from §3. Fills a gap `docs/ASSET_PIPELINE.md` left open (it has naming/import conventions but no canvas size, perspective, or roster).
- **RZ-085 — Armory/Upgrade screen** (`game/scenes/Armory.tscn`, `game/scripts/ui/Armory.gd`, `game/scripts/ui/MissionPrepController.gd`, `game/scripts/mission/MissionController.gd`): new Armory screen (UX_UI.md §6) reached from a new "Armory" button on Mission Prep's bottom bar (`[Back]` returns there — no Campaign Map to reach it from yet, RZ-080/081/082). Select a commander from a roster strip, then switch between three tabs. **Class Tiers**: spends `Economy.upgrade_cost()` via `RunState.spend_gold()`/`update_roster_meta()` — a real level bump that changes the squad's stats next mission via `UnitData.get_level_stats()`. **Relics**: spends `Economy.relic_cost()` and sets `Commander.relic_id` directly (already round-tripped by `SaveManager`; the relic's actual combat effect remains the pre-existing RZ-109 gap). **Abilities**: informational only — shows the class's ability name and `Economy.ability_cost()`, but no purchase button, since nothing in `MissionController`/`AbilityRegistry` currently gates ability activation by level or purchase (every class's ability already works unconditionally, contradicting GDD's "L2: ability purchasable" intent). Deliberately deferred rather than folded in here, since it would touch the same ability-activation code path RZ-143 found silently broken for months — tracked separately as **RZ-144**. Also fixed a related latent bug found while writing the Abilities tab: `class_data["ability_id"]` is JSON `null` for a class with no ability (Recruit) — `.get("ability_id", "")` doesn't fall back to `""` when the key exists with a `null` value, so assigning it straight to a `String`-typed variable would be a runtime type error. Fixed in both the new Armory code and the pre-existing `MissionController._squad_ability_id()` (not currently exercised — no promotion flow exists yet to ever produce a live Recruit-class squad, RZ-087 — but a real landmine for whenever it does).
- **RZ-089 — Run-over detection (total wipe) + summary screen** (`game/core/run/RunState.gd`, `game/scripts/mission/MissionController.gd`, `game/scripts/ui/HUD.gd`, `game/scripts/ui/MissionPrepController.gd`, `game/scenes/RunSummary.tscn`, `game/scripts/ui/RunSummary.gd`, `schemas/save_file.schema.json`): new `scenes/RunSummary.tscn` screen (UX_UI.md §8) shows "RUN OVER" (the wireframe's alternate "CITY SECURED" for full campaign completion never fires yet — no `CampaignState` to detect it, still blocked on RZ-081), commanders lost, and a new `RunState.total_safehouses_saved` running total (`SAVE_VERSION` bumped to 2; `from_save_dict()` defaults it to `0` for an older v1 save); `[Start New Run]` returns to the Main Menu. Reached from `MissionController._on_resolution_continue_pressed()` when `RunState.is_run_over()`, or directly from `MissionPrepController._ready()` if it ever finds an empty roster. **Also fixes a real gap this surfaced**: the mission resolution panel (`HUD.show_resolution()`) had no way to leave it at all — no button, no scene transition — so the player was stuck there after every mission, win or lose, regardless of run state. Added a `resolution_continue_pressed` signal off a new Continue button there, matching UX_UI.md §5's own wireframe (which already specified this button).

### Fixed
- **RZ-143 — `EnemyAI.gd` and `MissionController.gd` had been failing to load in the real Godot engine since the original bootstrap commit**, undetected through every prior "CI confirmed green" claim in this changelog and in `docs/HANDOFF.md` up to today: `game/core/enemy/EnemyAI.gd`'s `_is_frontal_attack` called `Vector2i.dot()`, which doesn't exist (only the float `Vector2` has it) — fixed by computing the dot product by hand (`to_enemy.x * facing.x + to_enemy.y * facing.y`). Both `EnemyAI.gd` and `game/scripts/mission/MissionController.gd` also had two `:=`-inferred-from-a-Variant-value declarations each (Godot hard-errors on this specific case, not a suppressible warning) — fixed with explicit `: Variant` / `: int` / `: bool` annotations in place of `:=`. None of this ever showed up in the Passed/Failed test count because no test file loads either script; it only appeared as `SCRIPT ERROR`/`ERROR: Failed to load script` lines earlier in the same `--import` step's log, which every previous "CI green" check in this project read past without inspecting. Practical impact: the mission scene could never actually have run in the Godot editor, since its own controller script failed to parse. Also fixed a same-day bug in `game/tests/test_commander_exposure.gd` (added with RZ-142): a plain `int` captured by a signal-connected lambda is captured by value in GDScript, so `func(_s): counter += 1` silently mutated a throwaway copy — all 5 of that file's signal-count assertions read back `0` instead of `1`. Fixed by capturing a single-element `Array` (a reference type) instead.
- `.github/workflows/ci.yml` downloaded a nonexistent Godot version (`4.3.0` instead of the correct release tag `4.3`), and `curl` lacked `-f` so it silently saved the resulting error page as `godot.zip` instead of failing loudly. Corrected the version string, added `-f`/retries, and a GitHub-release fallback if the tuxfamily mirror is unreachable.
- CI: added a `godot --headless --path game --import` warm-up step before running tests — a fresh checkout has no `.godot/global_script_class_cache.cfg` yet, so a bare `--script` invocation failed to resolve any cross-file `class_name` reference (`Identifier "X" not declared in the current scope`). Also made `game/tests/run_tests.gd` `preload()` its four test-file dependencies instead of relying on the global cache for those specific references.
- `game/data_runtime/UnitData.gd` — `get_class()` shadowed the native `Object.get_class()` method, a fatal compile error that cascaded into `CombatResolver`, `BreachAbility`, `AbilityRegistry`, and `DataLoader` all failing to load. Renamed to `get_unit_class()` (and updated its call sites in `Squad.gd`, `MissionController.gd`).
- `game/core/combat/CombatResolver.gd` — the `staggered` local variable failed Godot's static type inference; added an explicit `: bool` annotation.
- `game/core/squad/Squad.gd` — `commander.died.connect(_on_commander_died)` was never disconnected, creating a Commander↔Squad reference cycle that Godot's `RefCounted` (no cycle collector) never frees; every mission ever played leaked one stale `Squad` (and its `Unit`s). Latent since Squad/Commander were first written, but far more consequential once RZ-141 made `Commander` persist across missions via `RunState` (previously both objects died together with the mission, capping the leak at one mission's worth). Added `Squad.disconnect_commander_signal()`, called from `MissionController._exit_tree()` for every squad whenever a mission scene ends.

**CI confirmed green** on `dev` commit `dd680cf`: both jobs pass, 29/29 GDScript test assertions pass — the first time this codebase has been confirmed to run correctly in a real Godot engine. (The pipeline was briefly removed by request and then restored once confirmed to be wanted; see git history on `dev` around commit `333e031` if that back-and-forth needs tracing — it doesn't affect current state.)

### Added
- **RZ-090 — Save/Load wired to Main Menu "Continue"** (`game/core/run/SaveManager.gd`, `game/scripts/mission/MissionController.gd`, `game/scripts/ui/MainMenu.gd`): `SaveManager` gained `DEFAULT_SLOT := 0` (v1 has no save-slot picker UI) so the slot number lives in one place instead of being duplicated between `scripts/ui/` and `scripts/mission/`. `MissionController._end_mission()` now calls `SaveManager.save(GameState.run_state, SaveManager.DEFAULT_SLOT)` unconditionally, win or lose, right after roster metadata/gold are updated — the only save checkpoint that exists (no mid-mission saves, ADR-0007). `MainMenu.gd`'s Continue button (RZ-074) already called `SaveManager.load()`/`has_save()`; this was the missing write side, so Continue is now actually reachable in a normal playthrough instead of permanently disabled.
- **RZ-088 — Permadeath flow: UI feedback** (`game/scripts/ui/HUD.gd`, `game/scripts/mission/MissionController.gd`, `data/audio_events.json`): `HUD` gained `show_toast(text, duration)`, a self-fading center-top label — `MissionController._on_commander_exposed()` now shows "%s is exposed!" plus a new `commander_exposed` audio cue (the actionable warning, since the player can still send help or use Breach), and `_on_squad_wiped()` shows "%s has fallen." alongside the existing `commander_died` cue. Both back up the squad button's own persistent "✕"/disabled state (`HUD.update_squad_button`'s `is_wiped` branch), which only communicates the loss if the player happens to already be looking at the HUD bar when it updates. All of RZ-088's deps (RZ-141, RZ-142, RZ-046) were already done, so this closes the backlog item outright — no engine-side gap remained, only the missing UI moment itself.
- **RZ-074 — Main Menu scene** (`game/scenes/MainMenu.tscn`, `game/scripts/ui/MainMenu.gd`, `game/scripts/Main.gd`): `Main.gd` is now a thin bootstrap that immediately hands off to `MainMenu.tscn` instead of calling `GameState.start_new_run()` and skipping straight into Mission Prep. New Run opens an inline difficulty-select sub-panel (Easy/Normal/Hard/Very Hard read from `data/difficulty.json`, plus an optional seed field) per UX_UI.md §1, then starts a new run and transitions to Mission Prep — the wireframe's own target ("→ Campaign Map") doesn't exist yet (RZ-080/081/082), so this is the same substitution `Main.gd` already made before this screen existed. Continue calls `SaveManager.load()`/`has_save()` against a single hardcoded save slot, disabled when none exists. Quit exits. No Settings screen (no spec exists yet) and no save-slot picker (v1 is single-slot). Built entirely in code, same convention as `MissionPrepController`/`HUD` (no hand-authored `.tscn` UI tree). **RZ-090's remaining scope narrowed:** the Continue button's load-wiring is done here; what's left for RZ-090 is deciding where `SaveManager.save()` actually gets called in the mission flow, since nothing does yet.
- **RZ-142 — Implement exposed-commander vulnerability (last-stand combat)** (`game/core/squad/Commander.gd`, `game/core/squad/Squad.gd`, `game/core/enemy/EnemyAI.gd`, `game/scripts/mission/MissionController.gd`, `game/tests/test_commander_exposure.gd`): `Commander` gained a duck-typed combat interface (`position`, `facing`, `is_alive()`, `to_combat_data(traits) -> Dictionary`, matching `Unit.to_combat_data()`'s shape — `damage: 0`, no armor, no shield, per GDD's "commander fights on alone" rule; only the not-yet-implemented Mountain trait would change that). `Squad._prune_dead_units()` now transitions a squad into "exposed" exactly once, the tick its last unit dies (or immediately, for a squad that starts with 0 units) — the commander takes the last-processed unit's position (or `deployment_center`, a new optional `Squad._init()` param, if there was no unit to inherit a position from) and `commander_lost` fires. `EnemyAI`'s `Unit`-typed annotations were loosened to accept the duck-typed Commander with no special-casing (ADR-0006). `MissionController` now includes an exposed-but-alive commander in the `all_units` array passed to `EnemyAI.tick_enemy()` each tick, and gives them a visible grid marker (`_create_commander_view()`, cleaned up on squad wipe). This closes the gap RZ-141 surfaced: permadeath (`Commander.apply_damage()`/`die()`) is now actually reachable through normal play, not just correctly wired to `RunState`. 4 new test cases in `test_commander_exposure.gd` cover the exposure transition (fires once, correct position), the zero-unit-squad edge case, the commander as a valid `CombatResolver` target, and the `died` signal firing exactly once.
- **RZ-141 — Wire `RunState` into the live mission flow** (`game/autoload/GameState.gd`, `game/scripts/mission/MissionController.gd`, `game/scripts/ui/MissionPrepController.gd`): `GameState` now holds a `RunState` instance (`GameState.run_state`) instead of loose seed/difficulty/gold fields; `GameState.start_new_run()` seeds the same 3 placeholder Riot commanders the slice always used, but recruited once into the roster instead of re-created every mission. `MissionController._spawn_squads()` sources squads from `RunState.commanders`/roster metadata (same `Commander` objects RunState tracks, so `commander.died` already reaches `RunState.on_commander_died()` with no extra glue) instead of hardcoding fresh instances; writes each surviving squad's post-mission unit count and mission gold back to `RunState` at mission end. `MissionPrepController` is now roster-size-aware (no more hardcoded 3 squads) and shows each squad button labeled with the commander's real name; `[Start]` is blocked with a clear message if the roster is empty (total wipe) rather than allowing an empty, auto-losing mission. HUD squad buttons also show commander names in-mission. **New gap surfaced and tracked as RZ-142:** nothing in the codebase ever calls `Commander.apply_damage()`/`die()`, so permadeath still cannot occur through normal play even though the wiring to `RunState` is correct and complete — `Squad.commander_lost` fires when a squad's units are wiped, but the exposed commander is never made vulnerable/targetable.
- **RZ-054/RZ-055/RZ-135 — RunState + SaveManager** (`game/core/run/RunState.gd`, `game/core/run/SaveManager.gd`, `game/tests/test_save_load_roundtrip.gd`): commander roster (with parallel class/level/unit_count metadata alongside each `Commander`), gold, a placeholder `campaign_state` shaped like `schemas/save_file.schema.json` (ready for the real campaign graph once RZ-080/081 land), permadeath tracking (`on_commander_died` removes roster metadata but keeps the fallen commander in the list for history), `is_run_over()` (wipe detection), and JSON save/load to `user://saves/<slot>.json`. `Commander.gd` gained `DEFAULT_MAX_HP` (deduplicating a hardcoded `20` in `MissionController`) and `restore_state()` (reconstructs alive/hp on load without re-emitting `died`).
- **RZ-075 — Mission Prep screen** (`game/scenes/MissionPrep.tscn`, `game/scripts/ui/MissionPrepController.gd`): shows the generated grid before wave 1, highlights a deployment zone, lets the player place each squad by clicking a tile, and only enables `[Start]` once all are placed (squad count was hardcoded to 3 at first; RZ-141 later made it roster-driven). `Main.gd` now boots into Mission Prep instead of straight into `Mission.tscn`. `MissionController._spawn_squads()` uses the chosen tiles via `GameState.mission_deployment_positions` (falling back to auto-placement if `Mission.tscn` is loaded directly).
